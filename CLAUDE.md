# Требования к разработке: ассистент с памятью

Правила взяты из `gonets` и `WeGo` (устав, `codestyle-node.md`, живой код) и сведены к объёму тестового на 2–3 часа.

Приоритет при конфликте: ТЗ → решение владельца → стиль проектов. Каждое отступление записано в §10.

## 1. Контракт ТЗ (нарушать нельзя)

- `POST /chat` принимает `user_id` и `message`, возвращает текст ответа агента.
- Стек: TypeScript, NestJS, LangChain или LangGraph.
- Ровно два инструмента агента: `save_preference` и `get_preferences`.
- Решение о вызове инструмента принимает LLM. Никаких регулярных выражений и поиска по ключевым словам в сообщении.
- `user_id` в инструмент подставляет код из запроса. В схеме аргументов инструмента этого поля нет, поэтому модель не может его выбрать.
- Повторное сохранение не создаёт дубликат, изменение заменяет старое значение.
- Память переживает перезапуск сервиса.
- Вход валидируется, ошибки LLM обрабатываются.
- Тесты не обращаются к настоящей LLM.
- Секреты не попадают в репозиторий.

## 2. Архитектура

Ports & Adapters, как в `gonets`. Инфраструктура собрана в `src/core`, `src/app.setup.ts` общий для `main.ts` и e2e.

```
src/modules/<module>/
├── domain/          # правила без HTTP и хранилища, чистые функции и типы
├── application/     # сервисы, порты, коды ошибок
├── infrastructure/  # реализации портов: хранилище, адаптер LLM
├── presentation/    # контроллеры и DTO
└── <module>.module.ts
```

- Порт: `Symbol`-токен и интерфейс. Сервис зависит от порта, а не от реализации.
- `domain` и `application` не импортируют `infrastructure` и не читают `process.env`.
- Контроллер без `if`, `switch`, `try/catch` и `process.env`: принял DTO, вызвал сервис, упаковал ответ.
- Контроллер не инжектит репозиторий.
- Переменные окружения проверяются Joi-схемой только в `src/core/env.schema.ts`. Мусорное значение роняет старт, а не становится молчаливым умолчанием.
- `ConfigModule` импортирует только `CoreModule`.

## 3. DTO и валидация (обязательно)

- Вход и выход лежат в разных файлах: `<entity>.dto.ts` и `<entity>.response.dto.ts`.
- Request DTO: `class-validator` и `@ApiProperty` на каждом поле, с лимитами длины и форматом.
- Response DTO: конструктор присваивает поля поимённо (`this.id = v.id`). `Object.assign` и `Partial<T>` запрещены. Сырые записи хранилища наружу не отдаются.
- Глобальный `ValidationPipe`: `whitelist`, `forbidNonWhitelisted`, `transform`, статус 422.
- `user_id` проверяется по белому списку символов и длине: он может попасть в путь к файлу.

## 4. Swagger (обязательно)

- UI на `/docs`, JSON на `/docs-json`, в production отключён.
- Каждая ручка описывается вместе с кодом: `@ApiTags`, `@ApiOperation`, тип ответа и все коды ошибок (422, 429, 502, 503, 504).
- На каждом поле DTO есть `example`.
- e2e проверяет, что ручка и её схема присутствуют в `/docs-json`.

## 5. Агент и память

Инструменты:

```
save_preference({ preferences: [{ category, key, value }] })   # upsert каждой записи по (user, category, key)
get_preferences({ categories? })              # без categories — оглавление, с categories — значения всех перечисленных тем
```

Модель памяти, ключи нормализуются (`trim`, нижний регистр):

```
{ "напитки": { "предпочитаемый напиток": "кофе", "рецепт кофе": "1 ложка кофе, 2 сахара" } }
```

- Дубликат невозможен по структуре: пара `category` и `key` является ключом объекта.
- Оглавление не хранится отдельно, а вычисляется из данных, поэтому не может разойтись с ними.
- Системный промпт требует: сначала получить оглавление, затем переиспользовать существующие `category` и `key`. От этого зависит замена значения вместо появления второй записи.
- `get_preferences` читает несколько тем одним вызовом: иначе модель читала одну тему и заявляла, что по другим данных нет.
- `save_preference` принимает список: у `gpt-oss` на Groq нет параллельных вызовов, и один факт на вызов упирал длинное сообщение в лимит токенов.
- После `maxToolRounds` обращений на чтение инструменты убираются из запроса (запись не считается, иначе потолок обрезает факты): модель отвечает по уже полученным данным. На настоящей модели встречался круг между оглавлением и подробностями, из-за которого пользователь получал ошибку при успешном сохранении.
- Неизвестная тема: ассистент говорит, что данных нет, и предлагает их добавить.
- Агент работает через порт, поэтому в тестах модель подменяется заскриптованной.

LLM: адаптер на `@langchain/openai` с настраиваемым `baseURL`. Подходит для любого OpenAI-совместимого провайдера, модель и ключ задаются в `.env`. Конкретный провайдер проверяется по его документации в момент подключения, а не по памяти.

## 6. Хранение

Один JSON-файл на пользователя в `data/users/`, за портом `PreferencesRepository`.

- Запись атомарная: временный файл, затем `rename`.
- Записи одного пользователя выполняются последовательно через очередь внутри процесса.
- Имя файла является SHA-256 от `user_id`. Иначе на Windows `Alice` и `alice` попали бы в один файл и нарушили изоляцию. Сам `user_id` лежит внутри файла.
- Повреждённый файл даёт ошибку и не затирается.
- Ограничение: один экземпляр сервиса. Записать в README.

Почему не Mongo: ТЗ не требует БД, а Mongo без Docker заставит проверяющего ставить сервер. Порт позволяет заменить адаптер, не трогая сервисы.

## 7. Ошибки

- Единый глобальный фильтр. `res.status()` по контроллерам запрещён.
- Машинные коды в snake_case: `validation_failed`, `llm_unavailable`, `llm_rate_limited`, `llm_timeout`, `llm_bad_response`, `internal_error`.
- Stack trace наружу не уходит.
- Вызов LLM имеет таймаут. Повторяется только то, что точно не выполнилось: сохранение уже могло пройти.
- Неудачный вызов LLM не должен портить сохранённые данные.
- Сбой хранилища прерывает запрос с `internal_error` и не передаётся модели: иначе она могла бы ответить «запомнил».

## 7.1 Очередь и повторы

- Порт `ChatExecutor`, реализация `BullmqChatExecutor`. Обработка по одной задаче в порядке поступления, лимитер `CHAT_MAX_JOBS_PER_MINUTE`.
- У задачи `attempts: 1` и `maxStalledCount: 0`: повтор всей задачи заново прогонит агента.
- Повторяется только вызов модели (`retryModelCalls`): 429 с учётом `Retry-After`, 5xx, сбой соединения, `tool_use_failed`. Встроенный повтор LangChain отключён: он считает любой 429 от Groq исчерпанной квотой из-за слова billing в тексте.
- Ожидание дольше `LLM_RETRY_MAX_WAIT_MS` не выполняется: сразу 429 с `meta.retry_after_seconds`.
- `test:e2e` работает без Redis, очередь заменена за портом. Сама очередь проверяется в `test:redis` на настоящем Redis.

## 8. Логи

Winston, консоль и файлы `logs/` с ротацией, как в `WeGo`. Пути и уровень задаются в `.env`.

Предпочтения и текст сообщений являются личными данными, поэтому в лог идут только метаданные: `user_id`, имя инструмента, длительность, код ошибки.

## 9. Тесты и сдача

- Unit: домен и сервисы на in-memory фейках порта, а не на моках вызовов.
- Интеграционные: настоящий файловый репозиторий во временной папке.
- e2e: приложение через `supertest` и заскриптованная модель, которая возвращает `tool_calls`.
- Обязательные сценарии: все пять шагов примера из ТЗ, изоляция пользователей, обновление без дубля, перезапуск (новый экземпляр приложения на той же папке), подмена `user_id` в аргументах инструмента, невалидный вход (422), ошибка LLM.
- Перед сдачей: `npm run typecheck`, `npm run lint`, `npm test`, `npm run test:e2e`, `npm run test:redis`.
- Зелёные тесты не доказывают работу с настоящей моделью. Сдача считается состоявшейся после прогона сценария ТЗ на настоящем сервисе и настоящей LLM. Факт прогона указывается в отчёте.
- README: запуск и тесты, настройка модели, примеры запросов, решения и упрощения, фактически потраченное время.

## 10. Запуск и отступления от стиля проектов

Запуск под отладчиком описан в `.vscode/launch.json`, по образцу обоих проектов: watch-режим, отладка `dist` и тесты, включая текущий файл.

| Правило в gonets и WeGo            | Здесь                     | Причина                                        |
| ---------------------------------- | ------------------------- | ---------------------------------------------- |
| Префикс `/api/v1`                  | Без префикса              | ТЗ называет путь `POST /chat`                  |
| Конверт `{success, data, ...}`     | Сохраняется, `data.reply` | Стиль проектов, текст ответа остаётся в ответе |
| RBAC                               | Нет                       | В ТЗ нет ролей                                 |
| Docker для всей инфраструктуры     | Только Redis              | Нужен BullMQ, решение владельца                |
| Nest 10                            | Nest 11                   | Новые проекты на актуальной мажорной версии    |
| Prettier из WeGo (двойные кавычки) | Prettier из gonets        | Стек gonets ближе: Nest, npm, jest             |

Nest CLI 12 падает на Node 22.14 с `ERR_REQUIRE_CYCLE_MODULE`, поэтому каркас создан CLI 11.

## 11. Решения владельца

- Авторизации нет: пользователь определяется по `user_id` из запроса, как в ТЗ.
- Сообщения обрабатываются через BullMQ на Redis. `POST /chat` ждёт результат задачи, контракт ТЗ не меняется.
