# Ассистент с памятью о пользователе

Backend на NestJS и LangChain. LLM-агент сохраняет предпочтения пользователя и использует их в следующих сообщениях.

## Запуск

Нужны Node.js 22 или новее и Redis для очереди сообщений. База данных не требуется.

```bash
npm install
cp .env.example .env
```

Укажите `LLM_API_KEY` в `.env`, затем поднимите Redis и запустите сервис:

```bash
docker compose up -d --wait
```

```bash
npm run start:dev
```

Вместо Docker подойдёт любой Redis 6.2 или новее с `maxmemory-policy noeviction`: укажите его в `REDIS_URL`. Без Redis сервис не запустится и сообщит об этом.

- API: http://127.0.0.1:3000
- Swagger: http://127.0.0.1:3000/docs
- Отладка в VS Code: панель «Run and Debug», конфигурация «API: отладка (watch)».

## Настройка модели

Подходит любой OpenAI-совместимый провайдер с поддержкой вызова инструментов. Настройки находятся в `.env`:

| Переменная     | Значение                                   |
| -------------- | ------------------------------------------ |
| `LLM_API_KEY`  | Ключ провайдера                            |
| `LLM_BASE_URL` | Адрес API. Для OpenAI строку можно удалить |
| `LLM_MODEL`    | Модель с поддержкой инструментов           |

В `.env.example` указан [Groq](https://console.groq.com/docs/openai) с моделью `openai/gpt-oss-120b`. Ключ создаётся в его консоли. Набор доступных моделей зависит от аккаунта, список возвращает `GET /models`.

На использованном ключе действовали лимиты 8000 токенов в минуту и 200 000 токенов в сутки на каждую модель. Лимит считается на организацию, поэтому новый ключ той же организации его не сбрасывает, а другая модель из `GET /models` работает. Один запрос может вызвать модель несколько раз. Поэтому очередь пропускает `CHAT_MAX_JOBS_PER_MINUTE` сообщений в минуту, а остальные ждут своей очереди. Если лимит всё же исчерпан, сервис ждёт `Retry-After`, а при ожидании дольше `LLM_RETRY_MAX_WAIT_MS` сразу отвечает 429 со временем повтора.

## Тесты

Настоящая LLM и `.env` для тестов не нужны. Redis нужен только для `npm run test:redis`.

```bash
npm test
npm run test:e2e
```

```bash
npm run test:redis
```

- `npm test`: домен, сервис и файловое хранилище.
- `npm run test:e2e`: приложение целиком со сценарной моделью, а также адаптер ChatOpenAI против локального HTTP-сервера. Очередь здесь заменена прямым вызовом агента.
- `npm run test:redis`: настоящая очередь BullMQ на Redis: порядок, лимитер, ошибки, таймаут ожидания, обрыв Redis.

## Примеры запросов

```bash
curl -X POST http://127.0.0.1:3000/chat -H "Content-Type: application/json" -d '{"user_id":"user-a","message":"Я предпочитаю чай"}'
```

```bash
curl -X POST http://127.0.0.1:3000/chat -H "Content-Type: application/json" -d '{"user_id":"user-a","message":"Какой напиток мне предложишь?"}'
```

В консоли Windows `curl` отправляет кириллицу не в UTF-8, и сервис вернёт 422. Там используйте Swagger.

Успешный ответ:

```json
{ "success": true, "data": { "reply": "Предлагаю зелёный чай." }, "meta": null, "error": null }
```

Ошибка:

```json
{ "success": false, "data": null, "meta": null, "error": "llm_unavailable" }
```

| Статус | Код                  | Причина                                                                |
| ------ | -------------------- | ---------------------------------------------------------------------- |
| 400    | `bad_request`        | Тело запроса не является корректным JSON                               |
| 422    | `validation_failed`  | Неверные `user_id` или `message`                                       |
| 429    | `llm_rate_limited`   | Исчерпан лимит провайдера, время ожидания в `meta.retry_after_seconds` |
| 500    | `internal_error`     | Внутренняя ошибка, в том числе сбой хранилища                          |
| 502    | `llm_bad_response`   | Модель вернула пустой ответ или зациклилась                            |
| 503    | `llm_unavailable`    | Провайдер недоступен или отклонил запрос                               |
| 503    | `queue_unavailable`  | Недоступен Redis                                                       |
| 504    | `llm_timeout`        | Модель не ответила за `LLM_TIMEOUT_MS`                                 |
| 504    | `chat_queue_timeout` | Сообщение не дождалось обработки за `CHAT_WAIT_TIMEOUT_MS`             |

## Принятые решения

- **Память из двух уровней.** `get_preferences` без аргументов возвращает оглавление: темы и ключи без значений. С `categories` возвращает значения всех перечисленных тем. Так модель получает только нужную часть памяти.
- **Обновление вместо дублей.** Запись определяется парой `category` и `key`, поэтому новое значение заменяет старое. Системный промпт требует сначала прочитать оглавление и использовать существующие имена.
- **Изоляция.** `user_id` берётся из запроса и закрепляется в инструментах кодом. В схеме аргументов инструментов этого поля нет.
- **JSON-файлы вместо БД.** ТЗ не требует базу, а файлы не нужно устанавливать. Хранилище скрыто за портом и заменяется одним адаптером. Запись атомарная, операции одного пользователя выполняются по очереди.
- **Имя файла является хэшем `user_id`.** Иначе на Windows `Alice` и `alice` попали бы в один файл.
- **Потолок обращений к памяти.** На настоящей модели встретился круг между оглавлением и подробностями уже после сохранения. После 5 обращений на чтение инструменты убираются из запроса, и модель отвечает по уже полученным данным.
- **Оба инструмента работают со списками.** Одно сообщение может затрагивать много тем, а `gpt-oss` делает один вызов за шаг. Все факты сохраняются одним вызовом и одной записью файла, несколько тем читаются одним вызовом. Иначе модель теряла часть фактов на лимите токенов и отвечала, что данных нет, прочитав только одну тему.
- **Очередь BullMQ.** `POST /chat` ставит сообщение в очередь и ждёт результат, поэтому контракт ТЗ не меняется. Сообщения обрабатываются по одному и по порядку, лимитер защищает лимит токенов провайдера.
- **Повторяется вызов модели, а не задача.** У задачи одна попытка: её повтор заново прогнал бы агента и потратил токены. Вызов модели повторяется при 429, 5xx, сбое соединения и отвергнутом вызове инструмента. Инструменты в этот момент не выполняются, поэтому записи не задваиваются.
- **Сообщения прошлого запуска отбрасываются.** Их HTTP-запросы уже оборваны. Задачи живут в Redis не дольше минуты после завершения, на диск Redis не пишет.
- **Сбой хранилища прерывает запрос.** Иначе ошибка ушла бы модели, и та могла бы ответить «запомнил».
- **Логи.** Winston пишет в консоль и `logs/`. В логи попадают только метаданные, без текста сообщений и предпочтений.

## Упрощения и ограничения

- Нет авторизации: `user_id` принимается на веру, как и предусмотрено ТЗ.
- Нет истории диалога: каждое сообщение обрабатывается отдельно, поэтому короткий ответ «да» на предложение ассистента не имеет контекста.
- Один экземпляр сервиса: очередь записи в файлы живёт внутри процесса, а при старте сервис очищает очередь сообщений.
- Redis нужен всегда: ради одного процесса это избыточно, но очередь выбрана осознанно.
- Модель может ошибиться: например, ответить «запомнил», не вызвав `save_preference`. Решение о вызове принимает LLM, код это не перепроверяет.
- Если клиент не дождался ответа, уже начатая обработка завершится сама и может записать данные.
- Качество замены зависит от модели: если она выберет другой `key`, появится вторая запись. Защиты от этого на уровне кода нет, решение остаётся за LLM.
- Нет инструмента удаления предпочтений: ТЗ его не требует.

## Проверка на настоящей модели

Сценарий из ТЗ пройден через очередь на `openai/gpt-oss-120b` с настоящим перезапуском процесса: пачка одновременных запросов, изоляция пользователей, замена значения, факты из разных тем одним сообщением, незнакомая тема. Ответы модели недетерминированы, поэтому автоматические тесты её не используют.
